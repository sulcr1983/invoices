### 3.2 重点方向的理由

**① 本地 OCR（RapidOCR）—— 优先级最高，收益最直接**
- 现状痛点：百度 OCR 按次计费、必须联网、Key 放在 `.env` 里（已有泄露面）。工厂/财务内网常见断网，此时整个识别链路只能退到 pdfplumber，扫描件直接不可用。
- RapidOCR 基于 ONNXRuntime，CPU 可跑、无 GPU 依赖、Apache-2.0 可商用，8.5k star，**今天还在推**。相比 PaddleOCR（92k star 但需 paddlepaddle 运行时，体积大、Windows 依赖重），更适合本项目的"绿色便携"定位。
- 落地方式：不改现有链路，只在 `is_baidu_ocr_available()` 为假时，把 RapidOCR 作为第三优先级兜底（OFD → PDF 文本 → RapidOCR → 百度云）。**纯增量，可开关**。

**② easyofd 替换手写 OFD 解析 —— 减 683 行为 ~100 行**
- 现状：`ofd_parser.py` 683 行支撑 5 种格式变体，`_extract_seller_from_texts` 与 `_extract_buyer_from_texts` 几乎逐行重复，税率归一化逻辑重复 5 次。
- easyofd（PyPI v20260427，2026-04 仍有更新）专做 OFD 读写，可直接取 XML/文本/图片。建议**薄封装**：保留现有对外函数签名，内部换成 easyofd，先用真实 OFD 样本回归比对字段一致率，再切换。

**③ ⚠️ PyMuPDF 的 AGPL 风险（必须知道）**
- PyMuPDF 是 **AGPL-3.0 / 商业双许可**。个人自用无碍；一旦对外分发（含打包给同事的便携版）或商用，AGPL 要求整个项目开源。
- 当前用途仅是"PDF 转图片给 OCR 预处理"。若只自用，可不动；若要分发便携包，建议换 `pypdf`（BSD）或 `pdf2image`+poppler，或者买商业许可。
- 这是**合规问题不是技术问题**，需要你拍板。

**④ 模糊去重（RapidFuzz）—— 补 MD5 的空子**
- 现状：只认 MD5。同一张票重新扫描/重新下载，MD5 变了就重复入库（叠加 P0-6 无唯一约束，风险翻倍）。
- RapidFuzz（MIT，4.2k star）可做"发票号相似 + 金额相等 + 日期相近"的二次判定，比 `invoices.py:269` 的 `invoice_num in fp.stem` 子串匹配靠谱得多。

**⑤ MCP：没有现成的，但值得自建**
- 实测 GitHub 搜索无成熟的"发票/票据 MCP server"；官方 `modelcontextprotocol/servers`（91,943 star）只有 filesystem/git/fetch 等基础件。
- 建议：把本项目 31 个 API 里的 4-5 个只读能力（查台账、查统计、查重复、查风险）封装成一个本地 MCP server，让你日常用 AI 助手直接问"这个月发票总额多少"。**工作量约 1 天，收益是交互方式升级。**

### 3.3 明确不建议引入的（避免过度设计）

| 方案 | 不引入的理由 |
|:--|:--|
| MinerU（83k star） | NOASSERTION 许可、体积大、面向 LLM 语料转换，与"个人轻量工具"定位不符 |
| PaddleOCR 全家桶 | 需 paddlepaddle 运行时，便携包体积会从 38MB 级涨到数百 MB，违背绿色便携初衷 |

| loguru 替换 logging | 真正的问题是"没调用 setup_logging"，换库治不了病根 |
